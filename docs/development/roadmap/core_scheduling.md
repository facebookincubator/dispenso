# Roadmap: core scheduling

Thread pool, wake, locality, task graphs, and futures.

Current architecture: [three_tier_scheduling](../architecture/three_tier_scheduling.md),
[wake_tuning](../architecture/wake_tuning.md); the wake cascade itself is documented in
`dispenso/detail/thread_pool_wake.h`.
Proposal: [barrier_dispatch](../proposals/barrier_dispatch.md).

## Backlog

- Steal-ring round-robin for non-sleeping placed scheduling: `scheduleImplPlaced` currently only pushes to steal rings when it can claim a sleeping thread. When no threads are sleeping, the task falls through to the central queue. A round-robin steal-ring path for pool-worker callers could improve locality by keeping work near the scheduling thread. Requires benchmarking to confirm benefit over the central queue path.
- Windows thread pool wake strategy tuning:
  - Current approach uses `WakeByAddressAll` in the Windows `EpochWaiter::bumpAndWakeN` whenever more than one thread waits. The primary benefit is **parallel wake-up**: all threads begin their OS-level wake simultaneously, rather than serially. Thread wake-up latency (scheduler, context switch, cache warm-up) dominates — the `WakeByAddress` syscall itself is fast (<1 us)
  - Secondary benefit: the scheduling thread makes one syscall instead of N, freeing it to enqueue work or start its own computation sooner. This matters because the scheduling thread cannot worksteal until the queue is saturated, so every microsecond spent in wake syscalls is a microsecond of dead time where neither the caller nor the (still-sleeping) pool threads are making progress
  - The increased spin constants (kBackoffYield=100, kBackoffSleep=120 vs Linux's 50/55) are complementary: keeping threads in spin phase longer avoids the expensive wake-up latency entirely. Sub-microsecond spin cost vs 10s-of-microsecond wake-up cost
  - Benchmarks showed WakeAll outperforms the macOS-style heuristic (`n >= sleeping/2` → wakeAll, else wake individually), but thresholds N/2, N/3, N/4 were tested — not smaller fractions like N/16 that might limit thundering herd while still avoiding serial wake overhead
  - The spin constant and WakeAll changes were not benchmarked independently
  - Investigate: (1) whether a lower threshold (e.g., `n < sleeping/16`) balances thundering herd vs parallel wake benefit, (2) whether the spin constants should be tuned independently, (3) steady-state single-task patterns where WakeAll wakes unnecessary threads
  - Requires Windows benchmarking access to validate
- NUMA and topology awareness (phased):
  - **NUMA-aware thread grouping**: `buildThreadGroups()` currently groups by L3 cache topology only. On multi-socket systems where NUMA node boundaries don't align with L3 boundaries (e.g., Intel Sub-NUMA Clustering), groups may span NUMA nodes. Add an option to respect NUMA boundaries in addition to L3 boundaries, so that memory allocated by threads in a group stays node-local.
  - Windows processor group support for >64 threads (less critical as newer Windows versions handle this automatically)
  - Topology query API: expose NUMA node count, core-to-node mapping, and inter-node distances (Linux: `/sys/devices/system/node/` or `libnuma`; Windows: `GetLogicalProcessorInformationEx`)
  - Per-NUMA-node thread pools: opt-in pool construction affinitized to a specific node, composable with existing TaskSet/Future APIs
  - NUMA-aware allocator: STL-compatible allocator for node-local allocation (`mbind`/`numa_alloc_onnode` on Linux, `VirtualAllocExNuma` on Windows), paired with first-touch initialization guidance
  - **>1024-CPU support in `CpuSet`**: `CpuSet` currently represents CPU IDs in `[0, 1024)` (Linux/FreeBSD `cpu_set_t` / `CPU_SETSIZE`; a 1024-bit array on Windows/macOS); IDs at or beyond that are ignored gracefully (no UB), so CPUs `>= 1024` just aren't bound or grouped. Raise the limit when hardware approaches it: dynamic `cpu_set_t` via `CPU_ALLOC` + the `*_S` ops on Linux, a wider bitset elsewhere. `CpuSet`s are allocated only at startup, so the cost is low (e.g. a `thread_local` scratch set avoids per-call allocation).
- Topology-aware and adaptive reader-writer locks (after NUMA/topology work above):
  - **Shard by topology, not by hash.** `DistributedRWLock<N>` hashes thread identity into a fixed `N` (default 16) cache-line-aligned sub-locks. That is topology-oblivious: two threads sharing a core can collide while two shards sit on different sockets. Once `CpuSet` exposes NUMA nodes and inter-node distance, size and index the shards by real domains instead. On most machines that lowers `N`, which shrinks both the per-instance footprint and the O(N) writer cost while improving locality.
  - **Footprint is the binding constraint today.** At `N=16` with cache-line-aligned sub-locks each instance is on the order of a kilobyte, which rules the lock out for per-object locking and confines it to a few long-lived locks. Any redesign should treat instance size as a first-class goal, not a side effect.
  - **Degrade instead of redirecting.** The current guidance is to switch to `std::mutex` once writes approach 10% of operations, which asks callers to know a ratio they usually do not. Published designs in this space adapt at runtime -- biasing toward readers and revoking the bias when writers show up -- so the lock degrades gracefully rather than requiring the caller to have chosen correctly in advance.
  - **Survey before building.** `DistributedRWLock` is loosely modelled on the distributed-reader-indicator line of work (Dice et al.). Bias-based designs address the footprint and writer-cost drawbacks directly, and the area has continued to move since. Review the current literature and pick whatever composes best with `RWLock` and `DistributedRWLock` as they then stand, rather than porting a specific paper.

- Bounded `PoolWakeState` reclamation:
  - **Problem.** `ThreadPool::resize()` retires the old `PoolWakeState` into a grow-only graveyard that is freed only at pool destruction (see `thread_pool.h`). This is intentional and correct: `schedule()` reads `wakeState_` lock-free and dereferences it (e.g. `totalSleeping()`), so freeing a retired generation during operation is a use-after-free against a concurrent reader (TSAN-confirmed; an earlier bounded variant that freed old generations was reverted for exactly this). Cost is one `PoolWakeState` (~O(numThreads)) retained per `resize()`; only a long-lived process doing hundreds of thousands of resizes accumulates meaningful memory, so it is bounded in practice.
  - **Goal.** Reclaim retired generations safely without taxing the `schedule()` hot path — no per-call reference count and no hardware fence on the reader side.
  - **Approach (asymmetric-fence / hazard-pointer reclamation).** Readers (`schedule()`) publish the `wakeState_` pointer they are about to use into a per-thread hazard slot via a *relaxed* store bracketed by compiler-only fences — nearly free, no atomic RMW, no contention (this is a published pointer, not a reference count). `resize()` (rare, may be slow) publishes the new generation, issues a process-wide "heavy" barrier, then scans all hazard slots and frees a retired generation only once no slot still references it. The heavy barrier supplies the ordering asymmetrically so readers pay nothing: `sys_membarrier(MEMBARRIER_CMD_PRIVATE_EXPEDITED)` on Linux, `FlushProcessWriteBuffers()` on Windows, and an `mprotect`-toggle (forces a TLB-shootdown IPI → per-core barrier) fallback for macOS and other POSIX. After the barrier, a reader either had already published the old pointer (the scan sees it and waits) or runs its load after the barrier and therefore observes the new generation — so a retired object can never be freed while a reader still holds it. (folly packages this as `asymmetric_thread_fence_{light,heavy}`; dispenso would self-implement to avoid the folly dependency.)
- CUDA graph mappings (TaskFlow has this; worth exploring for dispenso's Graph)
- Speculative `Future` latency: the `future_benchmark` speculative suite runs ~1.5-3x behind `folly::Future` (while dispenso is ~2.2x faster on the kv-cache workload), so the gap is speculative-execution-specific — worth profiling folly's speculative fast path. What the suite measures is time to the first result, so look at how quickly the first candidate starts running after it is scheduled, and at whether the stealing order favours finishing one candidate over starting all of them.
- **Task chains on a mostly idle pool.** In `idle_pool_benchmark`'s `mostly_idle` case each task schedules the next, so one task is runnable at a time and the rest of the pool is idle. dispenso is level with or ahead of TBB at 1-2 threads on Windows and macOS, but from 4-8 threads up it trails on every platform, typically by 5-20x on wall time and by 40-280x at high thread counts (Linux from 32 threads, Windows from 16, macOS at 8-12). On Linux, a 1K-task chain takes 31-51 ms from 32 threads up against TBB's 0.14-2.6 ms, and dispenso uses more process CPU too up to ~64 threads. TBB's `task_group::run` from a worker pushes onto that worker's own deque, so the chain stays on one warm core without waking anyone. Find out where dispenso's chain loses its time (wakes, the shared queue, or thread hand-offs), and whether a task scheduled from a pool thread can run there next. See [the investigation](../investigations/idle_pool_wake_latency.md).
- **Responsiveness versus idle CPU as a pool setting.** `idle_pool_benchmark` shows the two goals pulling apart. On Linux (EPYC, 2 to 166 threads) dispenso uses 25-67x less process CPU than TBB across a 100 ms idle period, and 12-34x less at 16-166 threads on a burst after 5 ms idle, at about the same wall time. On macOS the two are close, and dispenso uses more while idle at 2-4 threads. Battery- and heat-limited devices (VR headsets, phones) want the low idle cost; latency-bound servers may prefer to spend CPU to wake sooner. Consider a per-pool setting (spin budget and wake policy) that picks the trade-off, with today's behaviour as one end of it. Judge any change on both wall time and process CPU, as the dashboard's idle_pool charts now show.
- **Scheduling many tiny tasks from one thread.** `simple_pool_benchmark` schedules N trivial tasks from the calling thread. On Linux (EPYC) `scheduleBulk` with 1M tasks takes ~10 ms at 1-2 threads and 1.2-1.6 s from 32 threads up; plain `schedule` jumps from ~6 ms at 2 threads to 0.5-0.8 s from 4 threads up. TBB degrades too, but more gradually. Find what the step at 4 and at 32 threads is (wake fan-out, queue contention, steal-ring sharing) before tuning.
- **Graph execution for compositing-style graphs.** `graph_compositing_benchmark` models a rendering compositor: many independent layer chains that join into a final composite. It has never been optimized for. dispenso's best variant is 7-12% behind Taskflow on Linux, macOS and Android, and 2.5x behind on Windows (0.97 ms vs 0.38 ms). Profile where the time goes per node; likely low-hanging fruit.
- **`parallel_for` locality on small inputs.** In `locality_benchmark` at 100K elements, dispenso's best time is at 4 threads and it gets slower beyond (0.26 ms at 4 threads, 1.5 ms at 128), while OpenMP keeps improving to 0.12 ms at 16 threads. At 4M and 32M elements dispenso beats TBB by 2.4-3.9x at 64 threads and up and is close to OpenMP, which pulls ahead at 4M from 64 threads up. Check whether a small input should be spread over fewer threads.
- Fork-join with heavy per-task work trails TBB. In `tree_benchmark`'s heavy-work cases (the binary tree with 10,000 iterations per node, and the 4-ary tree), both `parallel_invoke` and `TaskSet::schedule` with inline recursion run 1.4-1.7x behind `tbb::parallel_invoke` on a 112-thread two-socket Xeon (measured 2026-10-29), and 1.3-1.45x behind in the published Linux EPYC results. With light or no per-node work they match or beat TBB. On the 4-ary tree the `scheduleBulk` variant (`BM_4ary_dispenso_bulk_reference`) reaches 1.15x, so how heavy tasks are submitted and placed (`TaskCost::kHeavy`) is the first place to look.
- `parallel_invoke` parity with hand-written `TaskSet` recursion. `parallel_invoke` is the API built for fork-join trees and should be the fastest way to write one. In `tree_benchmark` it runs within 0-7% of `schedule` plus inline recursion on every workload, but behind under heavy work (4-ary tree: 23.8 ms vs 22.7 ms; binary tree with heavy work: 20.9 ms vs 19.6 ms, same machine as above). The 4-ary benchmark's comment points at the `OnceFunction` array indirection as the difference.

### Code TODOs

Open `TODO` comments in the source, each named by file and function. See
[the README](../README.md#conventions) for how these are kept in step.

- **Timed waits restart their timeout after a spurious wake.** `CompletionEventImpl::waitFor` (`dispenso/detail/completion_event_impl.h`, all three platform implementations) computes the relative timeout once, before its wait loop. A wake that doesn't complete the event waits the full timeout again, so `wait_for` can overrun the requested time. Decide whether to recompute the remaining time on each pass.
- **Future-level cancellation token** (`benchmarks/future_benchmark.cpp`, the speculative `when_any` suite). With a token, `when_any` could cancel the losers: it would skip losers that haven't started on a saturated pool, and let user kernels short-circuit cooperatively. Running tasks still run to completion. The benchmark's PauseTiming/drain workaround goes away once this exists. Related: cancellation in the [coroutines proposal](../proposals/coroutines.md).
- **Unwrapping constructor for `Future`** (`dispenso/future.h`, from the Concurrency TS: a `Future<Future<T>>` converts to `Future<T>`). `tests/future_test.cpp`'s tree-building tests would be simpler with it.
- **Cheaper `when_all` shared state** (`dispenso/detail/future_impl2.h`, both `when_all` overloads). They allocate their shared state with `std::make_shared`; an allocation through `SmallBufferAllocator` may be faster.
- **Graph allocator cache sizes** (`dispenso/graph.cpp`, `kMaxCache` and `kMaxChunkCapacity`). Per node type, the node-pool cache keeps up to 8 released allocators, each with capacity under 2^16 nodes. Make the limits macro-configurable for memory-constrained platforms.
- **Lock-free queue for `TimedTaskScheduler`** (`dispenso/timed_task.h`). The queue is a `std::priority_queue` under a mutex. The comment expects little benefit, since timed tasks rarely contend heavily; measure before changing it.
- **Taskflow partial-evaluation variant** of the scene-graph benchmark (`benchmarks/graph_scene_benchmark.cpp`), possibly with Taskflow's conditional tasks, to match dispenso's partial-evaluation case.
- **Portability of `platform.h`.** `DISPENSO_THREAD_LOCAL` supports only GCC, Clang and MSVC, and fails to compile elsewhere. `cpuRelax()` is a no-op except on x86, 64-bit ARM, PowerPC, and 32-bit ARM under MSVC; that includes 32-bit ARM with GCC or Clang (which has `yield`) and RISC-V (which has `pause` in Zihintpause).
